# Super Dev 项目演进与贡献准则

> 版本：1.0；2026-09-06 用户确认。适用于维护 `mixyoung/super-dev` 本身的开发者和模型。
> 本文是本项目演进边界与贡献准入的权威说明，不是给普通 Super Dev 用户增加的新开发流程。

## 1. 不随执行模型变化的方向

保持宿主内使用方式，以真实开发问题为起点，择优吸收有证据的知识和方法，通过有界验证改善交付质量。模型、来源和实现可以变化，产品方向、授权与验收标尺不能由一次任务自行重定义。

- 宿主负责模型、工具和实际执行；Super Dev 保留方法、知识、既有流程与确定性检查。不因借鉴外部项目引入独立模型运行程序、第二状态机或新主要入口。
- 保留标准九阶段、文档确认、预览确认及 SEEAI 的既有差异。新知识不得静默改变阶段、确认权、权限或质量阈值。
- Forge、需求审查、Grill、调试、TDD 等按问题使用，不以品牌名叠加必经步骤。
- 一个任务保持一个完整流程所有者、明确范围和工作区写入者。新来源不是新增执行权限。
- 正确交付优先于增加规则、文件、角色、分数或测试数量；未知不得算通过。

以上不是永远不可变，而是改变时必须提出独立的产品/架构决定，解释必要性、迁移和回退，并由项目维护者明确批准。普通知识吸纳不获得该权限。

## 2. 三层内容与决定权

| 层次 | 内容 | 决定方式 |
| --- | --- | --- |
| 产品核心 | 定位、主流程、确认权、权限、质量与证据语义 | 单独说明核心影响，由维护者批准；不能夹带在普通更新中 |
| 通用方法 | 需求、调试、测试、评审与交接方法 | 证明已有缺口、适用性和无回归后增量采用 |
| 场景知识 | 框架/API 版本、平台、行业及案例 | 按目标版本和真实需要核对；不自动影响无关项目 |

贡献者/模型可以研究、提议并执行已授权范围，不能以自评分、多数模型赞成或自行填写“已批准”代替维护者决定。审查者看原始证据，不只看作者总结。语义正确性与价值取舍必须人工审查；程序只检查它能确定的事实。

## 3. 贡献者从哪里开始

1. 阅读本文件与 [贡献指南](../CONTRIBUTING.md)，核对当前任务、分支和已有未提交改动。
2. 知识/方法更新遵守 [知识维护策略](../knowledge/00-governance/maintenance-policy.md) 的六问与适用性要求；用 [评审清单](../knowledge/00-governance/review-checklist.md) 复核。
3. 模型执行前说明本轮目标、允许改动与所读准则；这只是便于复核的回执，不是“已遵守”的证据。
4. 不自动读取 `AGENTS.md` 的工具，由任务发起者显式提供本文件和本轮范围。仓库内模型入口 `AGENTS.md`、`CLAUDE.md` 只保留指向本准则的短入口，不复制完整政策。

本项目专用规则不得写进 `super_dev/skills/skill_template.py` 或发布给普通用户的模板。产品 Skill 内容仍只改唯一模板，再运行 `python scripts/sync_super_dev_skills.py --write`；默认只同步仓库副本。

## 4. 每批留下可复核的吸纳记录

涉及知识、专家、产品提示/模板或核心合同的贡献，在已经确认的当前 change 下增加/更新 `adoption.md`。不得按最新时间猜 change；不得改另一 change 的状态或证据。普通无关代码改动不额外建立吸纳记录。纯排版/链接修订可用短记录，说明“无语义变化”及检查依据，不被迫编造性能试验。

记录使用以下二级标题，每项给实际内容，不照填空话：

- `## 问题与现有覆盖`：为什么改，已有哪里重合或不足。
- `## 来源与适用条件`：来源、固定版本/提交或核对日期，适用与不适用场景。无外部来源时写明本地依据。
- `## 取舍与核心影响`：具体改善、代价、不采纳项；是否改变核心/验收标准及批准依据。没有批准就如实写待决定。
- `## 改动范围`：逐行用 `- 路径` 列出本批涉及的仓库相对文件，包含删除/重命名前后的受影响路径；不用通配符或目录代替边界。
- `## 验证与未验证`：原基线、实际命令/环境/结果及原始证据、未验证项；行为样例同时包含正例和不适用反例。
- `## 决定与回退`：采用、试验、已有覆盖、暂缓、拒绝或纯编辑，以及理由、决定人/依据和回退方法。模型不得伪造维护者批准。

记录可引用原需求/架构/测试报告，勿复制第二份需求、词表或运行台账。仅填全字段不等于正确、更优或已经获准合并。

## 5. 固定验收，允许知识进步

- 对照修改前后的同一代表性任务，检查需求达成、旧能力、范围、权限、用户负担及适用平台；不按模型自评分或新增行数判断。
- 稳定案例见 [行为基准](../tests/fixtures/knowledge_adoption_cases.json)。期望行为对评估者隐藏，由审查者比对实际回答、文件和操作；这些数据本身不是已执行评测。
- 换模型时仍使用同样任务与验收依据，并记录真实模型标识、版本、宿主、证据和未覆盖范围。没测某模型/平台就写未验证；独立上下文不等同不同模型。
- 新增或改变方法时按风险选案例；不要要求纯文档排版运行所有模型。能力不足时缩小执行任务或补审查，不能放宽标准。
- 验收基准的语义变更需独立说明与维护者审查。合法需求变化允许更新测试；不能在同一实现中悄悄删掉失败案例或调低门槛后自证通过。
- 按需增加或修正已证实失败的用例；保留原基线，回退只针对本批差异，禁止整库覆盖/重置用户工作。

## 6. 机械检查与真正的合并约束

本地运行：

```text
python scripts/check_contribution_policy.py --base HEAD
python scripts/sync_super_dev_skills.py
pytest tests/unit/test_contribution_policy.py -q
```

`--base` 应是本次任务开始时或 PR 的真实基线；本地检查包括已暂存、未暂存及未跟踪文件。CI 从事件取得基线，手动触发检查上一提交至当前版本；缺失/无效基线报错，不猜最新 change。检查覆盖：入口仍在、行为基准结构有效、受控文件改动有本批非空记录且范围覆盖、同一受控文件没有被多批记录同时认领。普通无关修订不被强迫填写吸纳记录。

这不替代原测试/同步检查，不增加质量分数，也不扫描关键字判定语义对错。脚本和 CI 可被有写权限的人修改；因此需要外部仓库权限保障：

- `.github/CODEOWNERS` 指定本项目维护者审查规则、知识、模板、核心合同、检查脚本与基准自身。
- 要真正禁止绕过，远端 `main` 还须配置 PR 合并要求、必要 CI 和对应维护者审查，限制直接推送/强推，并处理管理员绕过权限。
- 本次只添加仓库文件，未修改远端设置。2026-09-06 只读核对时 `main.protected=false`、规则集为空；推送后仍需核对 CI 与远端保护再宣称强制生效。
- `@mixyoung` 是当前仓库所有者；只有一个维护者时，其本人不能批准自己的 PR。启用强制审查前要确定其他有权限的审查者或明确的维护者例外，不能假造第二审批人。

GitHub 机制依据：[CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)、[分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)。CODEOWNERS 需进入目标分支才影响后续 PR；本地文件不是远端已生效证明。

## 7. 更新与发布

源更新、真实失败或项目需求触发复核，只产生候选，不直接覆盖正式知识。既有内容仍按实际版本使用；时间到期触发核验，不自动删除或重组。证据不足先保持原规则，阻断性问题单列。

采用以明确范围、验证和批准为依据，发布/提交/推送遵守本次实际授权。核心准则本身修订时记录版本、原因和批准，不把模型能力变化视为修改路线的理由。
