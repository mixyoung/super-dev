# 系统化假设驱动调试法 (Systematic Hypothesis-Driven Debugging)

> **核心哲学**：永远不要在没有明确假说的情况下同时修改多个变量。真正的调试是科学实验——单一假设、最小复现、亲眼观测失败，验证闭环。

---

## 1. 散弹枪调试 vs 系统化调试

| 维度 | ❌ 散弹枪盲目调试 (Shotgun) | ✅ 系统化调试 (Systematic) |
| :--- | :--- | :--- |
| **面对报错** | 凭直觉猜测，同时修改 3~5 处疑似代码 | 先审查错误堆栈，只提出**一个**可测试的根本原因假设 |
| **复现方式** | 刷新页面看运气，或者依赖外部复杂环境 | 提取出一个最小的可执行失败单测或独立复现脚本 |
| **修改前提** | 没看到真实失败就直接写补丁 | **必须亲眼在终端看到断言因预期原因失败** |
| **完成标准** | 报错消失就立刻收工 | 断言变绿，且运行全量相关回归测试，确认无伴生破坏 |

## 2. 调试标准五步法

```text
[Step 1: 症状记录] ──> [Step 2: 单一假设] ──> [Step 3: 最小复现] ──> [Step 4: 定向微创修复] ──> [Step 5: 无损验证]
```

1. **Step 1: 症状与不变式审计**：
   - 记录期望的系统不变式（Invariant）是什么；
   - 记录实际观测到的偏离表现（精确错误信息、返回值、异常状态）。
2. **Step 2: 制定单一假设 (Single Hypothesis)**：
   - 用一句话写出：“我认为报错是因为在 [X 条件] 下，[Y 变量] 未被正确初始化/释放”。
3. **Step 3: 最小实验复现 (Reproduce)**：
   - 编写一段只覆盖该假设的单元测试或最小调用代码；
   - 执行它，必须观察到错误被稳定复现。
4. **Step 4: 定向微创修复 (Minimal Fix)**：
   - 仅针对该单一原因修改最少的代码行数；
   - 绝不趁机捎带做未经验证的“顺手重构”。
5. **Step 5: 验证与反思 (Verify & Assert)**：
   - 运行该测试变绿；
   - 运行上一级模块全量测试确保无破坏；
   - 将该复现测试永久保留在测试集中防止未来回归。

## 3. ⚡ Super Dev 流水线全自动注入路径 (Automatic Pipeline Injection)

本方法是 Super Dev 质量与修复流程的内置基石，**无需用户记忆口令，在任何报错与测试失败时自动装载**：

- **触发阶段**：`frontend`（前端运行时修复）、`backend`（后端实现与联调）与 `quality`（质量门禁）阶段。
- **生效角色**：`DEV`、`QA` 与代码修复循环（`TaskExecutor` / `QualityGate`）。
- **底层机制**：
  - 代码库内置完整的调试行动手册（`knowledge/development/02-playbooks/debugging-playbook.md`）；
  - 当单元测试失败或构建报错时，`super_dev/experts/toolkit.py` 自动加载调试 Playbook；
  - 模型被底层规则严格约束：在未生成最小复现单测并在终端看到真实报错前，**严禁修改任何业务源码**；
  - 修复后强制运行全量回归，断言变绿方可通过质量门禁。
