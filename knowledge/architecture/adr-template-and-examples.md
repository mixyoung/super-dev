# 架构决定、未决事项与交接记录

> 关键技术选型与重大架构决策强制要求双方案比对（Design It Twice），提供至少两个结构独立的备选方案及优劣权衡；对未决事项保持上下文保真与交接记录。
> 原知识条目：Excellent（11964948@qq.com）。2026-09-06 补充 UmaDev 未决事项与上下文保真；2026-11-24 增补 Matt Pocock (REF-005) 双方案比对设计法。

### 目标
- 对关键架构决策形成可追溯记录，降低后续误解与返工。

### ADR 标准结构
- 背景：当前问题、约束、目标。
- 备选方案：至少 2 个可行方案及优劣对比。
- 决策结果：选择方案与核心理由。
- 影响评估：性能、成本、复杂度、组织影响。
- 风险与回滚：失败情境与回退路径。
- 验证计划：上线前后验证指标。

### 双方案比对设计法则（Design It Twice）

> 参考 Matt Pocock (REF-005) 工程设计方法。在做出关键技术选型或重大模块架构时，强制要求产出至少两个结构独立的备选方案，防止陷入“第一直觉方案”的局部最优陷阱。

1. **强制双向推演**：
   - 面对高复杂度架构问题，禁止直接只给单一方案并顺理成章地宣布“这就是最佳解法”；
   - 必须构想出结构明显不同的备选方案（例如：方案 A 采用同步事务直写，方案 B 采用消息队列异步最终一致性；方案 A 采用轻量进程内嵌入，方案 B 采用独立微服务拆分）。
2. **四维硬性对照**：
   - **实现复杂度**：两者的代码量、状态复杂度和理解心智成本；
   - **故障模式与恢复**：挂掉时的表现是什么？如何排查？如何自愈？
   - **运维与交付负担**：需要新增哪些外部中间件、依赖或监控指标？
   - **回退与演进弹性**：如果未来业务方向调整，推倒重来的成本有多高？
3. **选型裁决依据**：
   - 选定方案必须明确写出：**“放弃另一个方案的核心原因是什么”**。只有讲清楚为什么不选 B，方案 A 的选择才具有真正的架构说服力。
4. **不适用反例**：
   - 常规 CRUD、修补拼写、单表增减列等日常低风险开发，严禁机械套用双方案推演，避免引入官僚主义开销。

### 命名规范
- `ADR-YYYYMMDD-主题.md`
- 示例：`ADR-20260306-api-versioning-strategy.md`

### 必填检查项
- 是否定义受影响模块清单。
- 是否明确兼容性与迁移策略。
- 是否给出最终废弃策略与时间点。
- 是否定义发布后观测指标。

### 常见失败模式
- 只写结论不写权衡过程。
- 没有更新历史 ADR 状态，造成“多版本真相”。

### 未决事项不等于已作决定

未确定的问题保留在现有需求、架构或项目决定记录中，不为了采用方法新建第二册。至少说明问题、来源、影响、当前倾向（若有）、阻碍条件和何时重新处理；负责人或期限只有确有安排时填写，不能编造。

恢复或开始相关工作时读回与当前任务有关的未决项。条件满足后就地记录结果和理由，保留历史；条件仍缺少时继续保留，不因文档存在就判已解决，也不把无关未决项全部升为当前阻断。

例如：数据量未知，暂用现有查询方式；当实际延迟或负载达到已约定的观察条件时再比较索引/缓存方案。记录条件与依据即可，不必现在增加缓存服务。

### 交接与压缩应保留的信息

- 当前目标、范围与已经作出的决定及理由。
- 已修改文件与当前代码版本，原始文件/证据的可访问位置。
- 实际执行的构建/测试命令、环境、结果与未验证范围。
- 未决事项、阻碍条件、下一项具体动作与仍需用户作出的决定。

沿用已有恢复简报或任务记录，摘要引用原文。恢复先核对当前文件和状态，再承接工作；不重新作已经确认的决定，不把旧通过结果默认为当前有效。只按需要读相关材料，不预先加载整库；不用这个原则另建记忆服务或自动知识系统。
