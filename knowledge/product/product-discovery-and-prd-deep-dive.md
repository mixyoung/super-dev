# 产品发现：价值判断、需求审查与业务术语

> 原知识条目：Excellent（11964948@qq.com）。方法吸收更新：2026-09-06。
> 适用于调研、需求与架构澄清。择优吸纳 Forge、需求审查与 Grill with Docs 的核心过程，不移植外部运行流程。

### 目标
- 把业务目标转化为可执行需求，保证“价值、可行性、可验收”一致。

### 关键方法
- 用户任务拆解：角色、场景、触发、行为、成功定义。
- 价值优先级：业务价值、用户价值、实现成本、风险敞口四维评分。
- 需求边界定义：必须做、应当做、可延后，避免范围失控。
- 验收标准前置：每个能力必须有可量化结果。

### PRD 必备结构
- 背景与目标
- 用户与场景
- 业务流程与状态流转
- 功能清单与非功能要求
- 数据与指标定义
- 风险与依赖
- 验收与上线条件

### 常见失败模式
- 需求写“功能名”而不是“用户结果”。
- 没有异常流和回退策略。
- 验收标准不可量化，导致开发与测试认知不一致。

### 执行清单
- 需求评审前完成术语统一。
- 关键链路必须补充时序图或状态图。
- 上线前确认指标埋点与监控项已对齐。

## 按缺口选择

先读当前需求、已有决定和相关代码。已回答的问题复用；只处理会影响本轮工作的缺口，信息充分时继续原流程。价值判断、需求审查与术语澄清没有固定先后关系。不要因为进入某个阶段就再次论证整个项目。

| 缺口 | 做什么 | 何时结束 |
| --- | --- | --- |
| 想法需要澄清、检验或改进 | 用 Forge 围绕中心主张逐步追问、反证与修正 | 形成可行动、待验证、缩小或暂缓结论与依据 |
| 不知道准确交付什么 | 检查角色、主流程、异常、权限、范围与验收；区分事实、暂定假设和未决事项 | 本轮关键歧义解决，其余事项有边界与重新处理条件 |
| 领域含义或设计取舍不清 | 用 Grill 对照文档与代码，按未决分支的依赖讨论 | 本轮关键决定写回原文档并通过场景复核 |

不要编造市场调研或用户证言；助手提出价值判断与建议，用户决定是否继续。商业项目考虑客户与收益，内部工具考虑效率与错误成本，学习项目考虑学习目标和投入，不统一强加盈利要求。

## Forge：澄清、检验与改进想法

从用户请求判断本次要澄清什么、检验什么或改进什么，不要求用户选择新的模式菜单。已有目标足够明确时直接引用；仅在不同解释会改变方向时确认。

1. **归纳当前主张。** 用一句话说明“谁在什么情况下，需要什么结果”，区分用户提供的事实、可核查证据和暂定假设。新项目读已有材料，增量工作先读项目当前约束。
2. **选关键问题。** 找出最可能改变投入或方案的假设。先查可查资料，再提出一个关键问题；同时给出建议、依据和最有力的反方理由。独立且低风险的小问题可合并，避免形式化逐问。
3. **根据回答修正。** 每轮明确新增了什么事实、推翻或保留了哪条假设，更新方案与理由；旧问题已解决就不重问。信息与原判断矛盾时可以改变建议，不为维护最初方案忽略反证。
4. **检验或改进。** 比较人工、现有工具、较小方案与原方案的收益、约束和维护成本。缺证据时提出能区分方案的低成本验证，写清观察什么；未做的试验不能写成结果。用户已知的内部需求不必重新证明市场规模。
5. **收敛并交接。** 关键问题已足以决定下一步时，给出可行动、仍待验证、缩小或建议暂缓的结论。说明采用/放弃的选项、理由、尚存风险与下一步。用户决定是否继续，不用模型分数替用户终止项目。

已获文档修改授权时，将结论定向更新到原调研的相关段落，保留未受影响内容；回读确认没有把假设写成事实。只要求讨论或评价时，先给结论和修改建议。可行动结论不等于文档确认通过，仍回到原 Super Dev 阶段。

例如：希望开发全天候 AI 报表，但尚不清楚谁阅读、据此做什么决定。可以先用人工摘要验证读者是否采取行动，再决定自动化范围。这是待验证的建议，不能宣称实验已有效。

对照：用户已明确为学习异步编程制作离线工具，时间预算和范围清楚。复用学习目标，帮助完成该范围，不再索要买家或付费证明。

## 需求审查：逐项对照、定向更新与复核

1. **建立本轮范围。** 读取现有 PRD、用户反馈以及已存在的架构/接口/任务，引用原需求编号或章节；不为审查另写一套 PRD。尚未进入 Spec 时不提前创建任务来填满追溯表。
2. **逐项对照。** 对本轮相关需求核对角色、输入、正常结果、异常/权限/边界、明确非目标与可执行验收。检查原需求和已有设计/任务是否互相支持；无关需求不要求重做，缺资料记为未知而不是已通过。
3. **提出发现。** 每项问题附原文位置、缺口或矛盾、影响及建议；只有影响本轮正确实现的歧义需要先解决。风格或未来功能归为可选，不放大成阻断。
4. **澄清决定。** 能从资料回答的先查；剩余关键问题提供建议与取舍，接收用户回答后更新发现。不得反复询问已回答的内容，不能用自动假设替用户作重要产品决定。
5. **定向落盘。** 获授权后只更新相关原需求和验收，保留稳定编号、原非目标和无关内容。只审查时交付发现与拟修改内容，不自行写入。
6. **复核闭环。** 回读修改后的原文，对照每个发现、用户决定、验收案例及已存在的设计/任务；说明已解决和仍未解决的内容。发现新矛盾时只重开受影响问题，非阻断事项记录影响与重新处理条件。

需要重新确认的产品/架构变化，交回原确认门；审查结束只表示本轮审查完成，不能替用户标记文档已确认、实现完成或发布通过。

例如：已有导出需求、字段与格式，但没有说明能否导出他人的订单。先指出权限缺口，再确认本人的订单与管理员范围，形成正常、越权和失败情况下的可验收结果。

对照：角色、权限、数据范围、失败表现和验收均已明确。直接复用这些决定；不要重问用户、重写另一份 PRD 或增加新的确认门。

## Grill with Docs：沿设计依赖澄清重要决定

Grill 不只检查词汇。它用于把领域含义、业务规则、接口边界和重要设计取舍说清楚；与 Forge、需求审查有交集，但只补未解决的部分，无需固定前置。

1. **先看文档和代码。** 找到现有词表、需求、架构/ADR 与相关实现，区分声明的预期和实际行为。没有代码就明确这一限制，不臆测实现。
2. **列出有用的决策分支。** 只列影响本轮的未决问题与依赖，例如“取消范围 → 可取消状态 → 退款规则 → 接口与测试”。先处理会改变后续答案的上游问题；小问题用短清单即可，不建设新决策树程序或固定全量问卷。
3. **逐分支讨论。** 用具体正常、异常或边界场景提出当前关键问题，附推荐答案和取舍。收到回答后更新已决定/仍未决及下游影响；已经明确且不冲突的选择保留，不因方法切换重复追问。
4. **落入唯一来源。** 获授权后把业务定义写回原词表、行为写回原需求、技术选择写回原架构，其他位置引用。只有难逆、需解释背景且有真实取舍的决定写 ADR；不为普通实现选择生成新文档。
5. **用场景回读。** 重新走一遍引发争议的案例，核对更新文档和已有接口/任务；代码尚未调整的差异明确留作待实现，不宣称靠改文档已修复代码。当前相关分支已解决或明确延期后结束，回到原流程。

业务词表记录领域含义，不用 JWT、Session 等通用技术缩写填充。先使用项目现有权威词表；无独立词表时写入 PRD 术语表。需要共享时才抽成单一文件，原位置改为引用。

每个需要澄清的概念说明定义、适用范围、易混淆概念和已知代码映射。不同上下文可有明确说明的同词异义；不要把所有字段机械改成同一名称。

例如：PRD 允许部分取消，代码只支持整单取消；取消和退款又被混用。用“一个订单有两件商品，只取消其中一件且付款已完成”说明冲突，明确预期后再更新定义与对应需求。读到旧代码不代表旧行为一定正确，用户新表述也不自动授权全量重构。

对照：领域中的客户对应代码 `Customer`，支付接口使用 `payer`，文档已说明付款方可以代付。该映射有业务意义，不是必须统一名字的错误。

## 结论落点与边界

- 价值判断和假设进入调研；需求、范围和验收进入 PRD。
- 业务定义进入已有共享词表或 PRD 术语表，其他文档引用；技术方案进入架构。
- 只有难逆、需解释背景且存在真实取舍的决定才写 ADR，普通选择留在架构中即可。
- 未决事项留在所属文档，记录影响和重新处理条件；恢复简报引用它，不复制第二套状态。
- 本轮关键歧义解决即结束追问。改变已确认需求或架构时遵循原确认流程，不因使用不同方法重新开题。

## 中断恢复与原流程兼容

需要暂停时，在当前工作文档记下已决定事项、关键依据、未决影响和第一步可继续动作；沿用现有恢复简报，只引用这些内容。恢复先读取再继续未决分支，不重新跑全部访谈。

这里吸收的是方法步骤，不能解释为新的阶段、自动状态机或门禁豁免。调研和三文档仍按原合同产出，文档/预览确认仍由用户作出，质量和交付仍要真实证据。纯审查不自动改文件，已批准的文档修订不重复索要同一授权；补齐文档也不自动授权代码、Git 或部署动作。

方法名称保留用于说明来源；不移植固定多角色表演、专属命令、独立日志体系、每轮全量设计树或无限追问。只有能帮助当前决定的部分才启用。

## 可验收需求与追溯（吸收 UmaDev 软内容）

把需求写成“在什么前提或事件下，系统对谁/什么产生什么可观察结果”。持续成立的规则可以直接描述，不要求所有句子套同一种模板。结果复杂时拆分可独立检查的行为，保留原需求编号；不要用“快速、友好、智能”代替验收。

例如“员工导出本人订单，越权请求返回明确错误且不返回订单数据”可以分别验证授权范围、拒绝行为与数据泄露边界。实际状态码、数量上限和性能目标沿用已确认合同；示例不能变成项目默认参数。

| 记录 | 应写什么 | 不能冒充什么 |
| --- | --- | --- |
| 需求 | 前提/触发、主体、可观察行为、范围 | 预先选定的技术方案或未要求的功能 |
| 验收 | 正常与适用的异常/边界/权限场景，验证办法 | 已经测试通过的结果 |
| 指标 | 目标、依据、测试环境或观察窗口 | 无依据的固定延迟/并发/转化率 |
| 追溯 | 原需求 → 验收 → 已有设计/接口 → 计划或实际验证 | 尚未创建的任务、尚未执行的测试 |

一项需求可以对应多项验证；一个回归测试也可以追溯到缺陷、不变量或兼容要求。只有进入原流程的相应阶段，才创建或更新 Spec 与实现任务。缺失项标明待设计/待验证及影响，不为了填满表格虚构证据。

新信息改变决定时，更新原条目并保留变化理由；不重新编号无关需求。详细的未决事项记录与交接方式见 [架构决定与未决事项](../architecture/adr-template-and-examples.md)。
