# 代码评审：范围、发现与交付证据

> 复杂变更审查按多视角审查集（Review Perspectives）与严格度档位聚焦架构一致性、安全防御、性能并发及契约兼容；交付证据需与主张严格对应。
> 原知识条目：Excellent（11964948@qq.com）。2026-09-06 增补 UmaDev 文档与报告源码中的证据组织方法；2026-11-24 增补 BMAD (REF-003) 多视角审查集与严格度档位。

### 1. 评审原则
- 评审关注正确性、可维护性、安全性、性能、可观测性。
- 评审意见必须具体、可执行、可验证。
- 对高风险变更执行严格评审等级。

### 2. PR质量标准
- PR必须聚焦单一主题。
- 变更必须包含测试与文档更新。
- 变更说明需覆盖影响范围与回滚策略。

### 3. 安全评审清单
- 是否存在越权风险与输入校验缺失。
- 是否可能泄露敏感信息。
- 是否存在危险默认配置。

### 4. 性能评审清单
- 是否引入额外高复杂度计算。
- 是否增加高频链路IO与序列化开销。
- 是否影响缓存命中与数据库负载。

### 5. 可运维性评审清单
- 是否补充关键日志与指标。
- 是否可在异常时快速定位问题。
- 是否可安全回滚到上一个稳定版本。

### 6. 评审闭环
- 阻断级问题必须修复后才可合并。
- 复发问题应沉淀到评审清单与模板。
- 评审质量按缺陷逃逸率持续优化。

### 7. 每项发现应可核查

用当前差异、需求与合同、相关上下文和实际验证结果判断。发现写明位置、触发条件、期望与实际差异、影响及修正方向。正确性、需求、契约、安全或数据完整性问题可以阻断；个人风格、未要求的新特性和可选重构不能冒充必须修正。

材料不足时说明未知和补证据的方法，不把“没找到问题”当作通过。隔离只读上下文才称独立评审；同一执行者复核应标为自检。评审意见不能自动确认用户文档、修改代码、合并或发布。

### 8. 汇报主张与证据对应

| 主张 | 核验内容 | 缺失时的表述 |
| --- | --- | --- |
| 测试通过 | 当前代码、范围、环境、退出码与原始报告一致 | 未运行或证据不可用 |
| 需求满足 | 当前验收场景与实现/运行证据对应 | 只有文档或待补运行验证 |
| 可发布 | 当前必要门禁与适用部署/恢复检查满足 | 指出缺口，不用局部测试替代发布判断 |

复用已有证据文件及其引用，不为同一事实生成多个独立来源。报告生成成功不证明证据齐全；存在代码或接口名称也不证明行为正确。

### 9. 按交付形态核验

线上服务需要与其风险相称的部署、故障发现与恢复证据。离线工具则检查安装/启动、输入输出和相关恢复路径，不强制其拥有云端运维体系。已有质量阈值和严重问题不得靠平均分抵消。

### 10. 多视角审查集 (Review Perspectives)

复杂变更或关键模块审查时，应避免一揽子泛泛而谈，按具体切面分组聚焦：
- **架构一致性视角**：核查模块职责划分是否清晰、是否存在过度耦合或循环依赖陷阱、是否破坏系统分层边界与既定架构决策（ADR）。
- **安全防御视角**：核查越权风险、输入校验与过滤缺失、SQL/命令注入、敏感凭据泄露及不安全的默认权限配置。
- **性能与并发视角**：核查高频链路耗时、高复杂度算法、线程安全与竞态条件、内存与连接池泄漏风险。
- **接口向后兼容视角**：核查公共 API 契约变更、数据库字段增删是否破坏现有下游消费者、数据序列化与平滑迁移策略。

### 11. 审查严格度档位 (Review Depth)

根据变更的影响范围与风险等级，动态调整审查严格度：
- **极简速审**：适用于纯文档修正、界面文案微调或开发配置补全。主要核对格式规范与基本准确性，不展开深层推演。
- **标准评审**：适用于常规业务特性或普通缺陷修复。核对单一职责、单测覆盖、异常边界及文档同步。
- **深度渗透**：适用于涉及身份鉴权、金融交易、高并发核心数据存储或底层通用基座改造。必须覆盖全部多视角审查切面，提供端到端回滚方案与充分的运行验证证据。
