# Plan: 周期性框架维护与知识边界加固

## Context
在不改变单一Core、标准九阶段、确认权和质量阈值的前提下，统一知识权威边界、阶段专家来源、专家工作契约、Spec前工作项绑定及交付事实语义。

## Architecture Impact
- Core 合同：在既有工作流合同旁建立可复用、类型化的内容权威定义；知识、专家、外部文档均不能直接产生阶段、权限、确认、发布或工作区所有权效果。
- 知识链：知识索引保持检索职责，注入时确定性构造紧凑信封；缓存只保存派生信息，不成为权限或确认真源。
- 专家链：`WORKFLOW_STAGE_EXPERTS` 保持唯一真源，兼容映射为不可写派生视图；画像加载保留 v1 兼容并补足 v2 工作契约。
- 工作项链：只扩展现有 `.super-dev/workflow-state.json`，标准流程从 baseline/research 使用 `work_item_id`；Spec 绑定前后使用同一身份。SEEAI 不变。
- 证据链：四类交付后事实和运营信号进入现有报告的可选字段，不进入九阶段枚举，不新建台账。

## Risks & Mitigations
- 知识信封误把适用约束降为建议 -> 旧知识在已命中适用领域时默认 `applicable_constraint`，同时用正反例验证；安全禁区与知识强制性分开表达。
- 新身份字段误伤旧状态 -> 读取路径兼容缺字段；只有明确的新 `work_item_id` 才启用严格绑定，且失败关闭不删除旧 change。
- 统一映射改变现有组合 -> 先冻结 canonical 组合；兼容视图从其派生并加不可写与消费者一致性测试，不修改 SEEAI 组合。
- ExpertProfile v2 造成覆盖文件失效 -> 新字段提供保守默认值；项目 > 用户 > 内置的优先级不变，未知字段不扩大权限。
- 交付事实被误当阶段或互相推导 -> 使用独立布尔/状态证据和 schema 验证；保持九阶段常量测试。

## Rollout Strategy
- 先完成 FR-01/FR-06 安全原子批，再完成阶段映射、画像、身份和交付事实；每批运行定向回归。
- 旧知识、ExpertProfile v1 和旧 workflow-state 保持可读；新字段均为向后兼容增量。
- 本轮只做本地实现与验证。提交、推送、合并、发布、部署和全局安装均需后续明确授权。
- 回退只撤销本 change 的差异；不重置工作树、不删除旧记录、不降低门禁。
