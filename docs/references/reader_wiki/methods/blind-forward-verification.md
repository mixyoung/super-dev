# 隔离前向盲测验证法 (Blind Forward Verification)

> **核心哲学**：不要拿着答案去考模型。先给答案的自测叫“欺骗自己”；只有把模型放进无先验知识的隔离沙箱中，按轮喂入案例并观察其能否自主达成期望状态，才是真正具备说服力的验证。

---

## 1. 为什么“事后自评”毫无意义？
很多开发者在测试自己写的 Prompt 或 Skill 时，会在对话一开始就把最终正确的代码或规范贴出来，然后问模型：“你觉得我的实现对不对？”
- 模型的回答必然是：“非常完美，完全符合规范。”
- 这种验证没有任何可信度，在真实生产场景中遇到全新问题时立刻崩溃。

---

## 2. 盲测执行协议

1. **环境完全隔离 (Isolate Environment)**：
   - 清理所有历史聊天记忆与临时环境变量；
   - 目标答案文件严禁出现在上下文或沙箱路径中。
2. **渐进供给案例 (Round-by-Round Injection)**：
   - 第一轮：仅提供普通用户的模糊原始需求；
   - 观察：模型加载的技能是否提示其去追问关键细节？
   - 第二轮：补充具体的边界业务数据；
   - 观察：模型产出的文件是否自动遵守了既定 Schema？
3. **确定性断言验收 (Deterministic Assertion)**：
   - 运行独立测试脚本，检查模型生成的代码是否真实通过编译与单测；
   - 检查产物是否包含必须的元数据，不依赖人工肉眼扫视。

## 3. ⚡ Super Dev 流水线全自动注入路径 (Automatic Pipeline Injection)

盲测验证法是 Super Dev 质量守门（`quality`）、CI 预检与贡献者准入的核心机制，**由测试框架与预检脚本自动执行**：

- **生效位置**：`scripts/preflight.sh`、`pytest` 单元/集成测试套件以及 `super-dev quality` 质量门禁。
- **底层机制**：
  - 在验证任何技能吸纳或规则更新时，测试用例（例如 `tests/unit/test_oil_tone_adoption.py`）采用独立上下文沙箱执行断言；
  - 严禁通过人工直接询问“这个生成得好不好”作为质量证据；
  - 必须通过确定性脚本测试、退出码校验和产物 Schema 断言，全绿方可放行交付。
