## 1. 背景与核心问题

UmaDev 包含庞大的 Rust 核心框架以及丰富的开发/交付规范。我们必须明确：
1. 哪些内容能解决 Super Dev 现有的交付痛点？
2. 哪些内容会破坏 Super Dev 原有的单 Core、九阶段主流程？

---

## 2. 决策结论

我们决定**仅吸收其 U1–U14 的“软内容规范”（需求因果表达、测试反作弊检查、未决事项登记簿、证据评审）**；**坚决不引入其 Rust 运行时二进制、不增加外部执行器依赖、不引入第二状态机**。

---

## 3. 详细取舍与负向边界 (Negative Boundaries)

### ✅ 为什么吸收软内容
- **消除需求幻觉**：EARS 规范让模型表达需求时必须给出触发条件与可观测结果，无法用空话搪塞；
- **堵塞测试漏洞**：测试完整性审查迫使模型在修改代码后不能靠注释断言或跳过用例来“刷绿”。

### 🛑 为什么坚决拒绝其余部分 (Why Rejected)
1. **拒绝 Rust 二进制与外部执行器**：
   - Super Dev 是运行于宿主（如 Claude Code / Gemini CLI / Codex）内的纯 Python 治理工具，引入外部 Rust 二进制包会破坏开箱即用性并增加跨平台编译负担。
2. **拒绝 `.umadev/coach` 状态机与新流程入口**：
   - Super Dev 拥有既定的标准九阶段与确认门禁。引入外部状态机会导致双头管理，使用户困惑。
3. **拒绝强制的固定阈值**：
   - UmaDev 示例中的具体 API 个数、延迟数值、覆盖率门槛仅为案例示范，不得作为全局硬门槛强制套用。
