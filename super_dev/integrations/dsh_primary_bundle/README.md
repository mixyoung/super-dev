# Super Dev 的 DSH 原生开发插件

这是主开发入口，不是状态伴生插件。它在 DSH `0.2.2-rc.3` 中注册 `/super-dev` 和 `/super-dev-seeai`，把已绑定任务的规则和明确用户需求交给当前 DSH 智能体。不需要项目级 DSH `SKILL.md`；不替换 DSH 的 `agent-instructions`，不改共享 Codex Skill。Python Core 持久化工作项和确认，插件不另存阶段。

## 本地配置

使用同版 DSH 官方本地组合包装载本目录或同字节的本地包；先在新隔离配置档验证，不用修改 DSH 安装包。`package.json` 的 `engines.dsh` 不替代实际版本核验。依赖存在、组合启用、原生加载和桌面安装是不同结果；不要用目录复制或 CLI 退出 0 假冒已在桌面启用。不自动迁移旧的项目 Skill 或写入现用配置档。

组合启用时给 `super-dev-dsh-primary` 配置一个位于被查询项目之外、实际安装该 Core 版本的可信 Python 绝对路径。插件只用这个解释器调用固定 Core 模块，不经 Shell、不读取模型密钥。以下路径仅为示例：

```yaml
- id: super-dev-dsh-primary
  config:
    pythonExecutable: 'C:\path\to\trusted\python.exe'
```

首版本地候选不授权受管会话的任意终端、程序化工具调用、子任务启动或未知工具；没有验证独立写入权限时，不提供绕过阶段限制的终端开关。不要把前置钩子视为终端沙箱。适用的标准流程在文档确认并生成 Spec 后，只能先写 `frontend/` 或 `output/frontend/` 下的前端文件；受管智能体不能创建预览通过报告。首版需由受信操作者通过既有前端运行验证入口生成真实证据，再回 DSH 核对及确认。没有证据不跳过预览。普通未绑定会话仍沿用宿主自己的工具与权限。

## 使用

- `/super-dev <需求>` 或 `/super-dev-seeai <需求>`：在已选择的本地项目开始同模式任务。若项目已被其他会话、模式或原接入绑定，不自动重置、接管或猜历史活动任务。
- 同一命令无参数：查看当前 Core 阶段和待核对版本，不启动回合。
- `/super-dev 确认基线 <摘要>`：已有项目先完成并核对本任务的基线审计，再进入差量调研。其他项目或旧版基线不能代用。
- `/super-dev 确认文档 <摘要>`：先核对输出目录中**当前任务**的三文档，使用同一会话回执中的完整摘要。SEEAI 使用自身命令；适用标准流程的预览用 `确认预览 <摘要>`。修改后需重新核对版本。进度消息、自动目标续轮、模型回复都不被当成批准。
- `/super-dev 继续当前流程` 或对应 SEEAI 命令：从当前 Core 状态继续。在文档已核对之后，由既有 Spec 生成器创建及绑定同一工作项，再投递下一阶段；未核对时仍停在原门，没有审批副作用。恢复原生会话时仅根据已经存在的命令日志和 Core 绑定核验，不依赖旧模型记忆。

移除只作用于该组合包；已保存任务和项目文件仍属于项目。卸载后的统一共享 Skill 来源问题（A12）不是插件能力。本地模块接入和离线测试不等同完整桌面、真实模型项目或默认迁移已经通过。
